# 메모리 사용량 개선

측정일: 2026-10-15. 변경 전은 `9c76c69`의 앱 코드입니다. 같은 Mac에서 같은 예시 계정 2개와 화면 전환 순서로 비교했습니다.

## 변경한 부분

- Windows·macOS: 계정·사용량 조회가 끝나면 해당 Codex 조회 프로세스를 종료합니다. 다음 조회는 새 프로세스에서 초기화합니다. 로그인 또는 요청이 진행 중이면 정리하지 않으며, 인증 파일·계정 목록·마지막 수신값·집계 기록은 유지합니다.
- macOS: 처음 카드를 열기 전에는 WebKit 화면을 만들지 않습니다. 카드를 닫고 5초가 지나면 화면과 메시지 연결을 해제합니다. 자동 조회와 메뉴 막대 애니메이션은 네이티브 호스트에서 계속합니다.
- macOS: 다시 열 때 자세히·간략히 보기, 설정 페이지, 펼친 계정, 저장 전 별명, 스크롤, 입력 포커스와 선택 영역을 복원합니다. 짧게 닫았다 열면 같은 화면을 사용합니다. 지난 회전은 재생하지 않습니다.

조회 주기, 최대 동시 조회 수, 삼각형 모양·물결·회전, 숫자·막대 효과, 계정 추가·삭제·로그인 방식은 유지했습니다. 운영체제에 강제 메모리 비우기를 요청하거나 공식 CLI의 인증 상태를 지우지 않습니다.

## 동일 조건 비교

아래 값은 앱과 macOS가 해당 앱에 배정한 보조 프로세스 전체의 **physical footprint**입니다. 압축된 메모리도 포함하므로 RSS 또는 Windows private working set과 직접 비교하지 않습니다. 단위는 MiB(1,048,576바이트)입니다.

| 상태 | 변경 전 | 변경 후 | 프로세스 수 전 → 후 |
|---|---:|---:|---:|
| 실행 후 카드를 한 번도 열지 않음 | 58.4 | 14.3 | 6 → 2 |
| 자세히 보기 | 117.5 | 114.4 | 6 → 6 |
| 간략히 보기 | 110.1 | 109.8 | 6 → 6 |
| 카드를 닫은 뒤 | 89.8 | 44.8 | 6 → 4 |
| 해제 후 다시 연 간략히 보기 | 104.6 | 94.1 | 6 → 6 |
| 닫기·열기 4회 후 다시 닫음 | 92.5 | 45.3 | 6 → 4 |

이 표본에서 카드를 닫은 상태는 약 **50%**, 처음 열기 전은 약 **76%** 감소했습니다. 닫힌 상태에서는 WebContent와 Networking 프로세스가 사라졌고, 화면을 다시 열면 필요한 프로세스를 생성했습니다. GPU 등 운영체제가 보관하는 보조 서비스는 이 짧은 측정 구간에는 남았으며, 이후 해제 시점은 운영체제가 결정합니다.

해제 후 간략히 보기 DOM이 다시 준비되기까지는 4회 기준 약 152~180ms였으며, 변경 전의 같은 화면 재사용은 약 11~38ms였습니다. 이는 카드 요소가 만들어진 시점까지의 시간이며 이후의 표시 애니메이션 완료 시간은 포함하지 않습니다.

### 측정 범위

- Apple Silicon, macOS 27.0.1에서 측정했습니다. 각 화면은 준비 시간을 둔 뒤 7초 동안 약 1초 간격으로 수집했고, 프로세스가 바뀌는 화면 전환 구간은 제외했습니다.
- `proc_pidinfo`로 앱의 resource coalition을 식별하고 `/usr/bin/footprint`로 해당 프로세스들을 함께 측정했습니다. WebKit뿐 아니라 앱에 배정된 macOS 보조 서비스도 포함했습니다. 측정용 조회 구조는 Apple의 [XNU 정의](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/proc_info_private.h)를 따르며 앱 실행 코드에는 들어가지 않습니다.
- 예시 데이터는 실제 CLI를 실행하지 않습니다. 따라서 표에는 Codex 프로세스 정리로 줄어드는 메모리가 포함되지 않습니다. 실제 로그인 상태로는 프로세스를 종료·재시작하면서 3회 연속 계정·한도 조회를 검증했고, 각 묶음은 약 0.82~1.20초였습니다. 모델 요청은 만들지 않았습니다.
- 짧은 로컬 비교이며 다른 Mac·계정 수·CLI 버전에서의 보장 수치는 아닙니다. 화면이 보이거나 조회가 진행 중일 때는 WebKit·CLI에 필요한 메모리를 사용합니다. Windows 전체 앱의 메모리 수치는 이번 Mac 환경에서 측정하지 않았습니다.

원시 표본과 화면별 집계: [변경 전 JSON](memory-before.json), [변경 후 JSON](memory-after.json).

## 재현과 기능 검증

macOS 앱을 빌드한 다음 새 출력 폴더를 지정합니다.

```bash
python3 MacUsageWidget/Tests/measure-memory.py \
  'artifacts/macos/AI Usage.app' artifacts/macos/memory-check

./MacUsageWidget/verify.sh

open -n 'artifacts/macos/AI Usage.app' --args \
  --fixture --data-dir "$PWD/artifacts/macos/memory-ui-data" \
  --smoke-test "$PWD/artifacts/macos/memory-ui-check" --verify-memory
```

`measurement.json`은 메모리 표본과 집계, `memory-benchmark.json`은 반복 복원 결과, `smoke.json`은 실제 WebKit 기능 검증 결과를 담습니다. 메모리 측정은 여러 번 닫고 열면서 약 2분 동안 실행되며 테스트 앱만 종료합니다.

Windows 프로세스 제어는 실제 앱의 C# 코드를 가짜 CLI와 연결해 독립적으로 검증합니다. 아래 프로젝트는 .NET 8을 사용할 수 있는 macOS에서도 실행할 수 있습니다.

```bash
dotnet run --project WidgetVerification/Portable/UsageWidget.ProcessVerification.csproj \
  -c Release -- artifacts/process-verification
```

이 검증은 반복 재연결, 실제 프로세스 종료, 인증 파일 보존, 요청·로그인 진행 중 정리 방지, 로그인 취소와 조회 오류 후 정리를 확인합니다. Windows WPF 앱과 통합 검증 프로젝트는 별도로 빌드합니다.

### 이번 변경의 검증 결과

| 검증 | 결과 |
|---|---|
| macOS 네이티브 로직·CLI·계정·집계 | 41개 통과 |
| 공통 UI 표시 시계 | 8개 통과 |
| Windows C# 조회 프로세스 종료·재연결 | 31개 통과 |
| Windows 계정 삭제 회귀 검증 | 22개 통과 |
| 실제 WebKit 화면 | 해제·재생성, 미저장 입력, 선택 영역, 스크롤, 설정·보기 모드, 새로고침·전환 회전 검증 통과 |
| 실제 Codex CLI | 서로 다른 조회 프로세스로 3회 연속 연결·조회 성공 |
| 실제 계정 2개를 연결한 macOS 앱 | 화면을 해제한 상태에서 자동 조회 후 두 조회 프로세스 모두 종료, 다시 열면 최신 값 표시 |
| 빌드 | macOS 앱 빌드·서명 검증 및 Windows WPF 앱·통합 검증 프로젝트 교차 빌드 성공 |

실제 계정을 연결한 앱을 닫고 78초 동안 별도로 관찰했을 때, 전체 footprint는 시작 46.1MiB에서 종료 시 29.6MiB였습니다. 이 사이 자동 조회는 유지됐고, 운영체제가 GPU·오디오 보조 서비스도 해제했습니다. 이 값은 위의 동일 조건 예시 데이터 비교와는 별도 관찰입니다.

Windows 전체 앱의 실행·화면 검증은 Windows 환경에서 별도로 필요합니다. 이번에는 Mac에서 실행 가능한 실제 C# 코드 검증과 Windows 대상 빌드까지 확인했습니다.
